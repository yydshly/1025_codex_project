# 实验：将模糊需求变成可验证的规格

## 目标与材料

围绕项目 009 的资料检索研究，构造一个贴近实际但只使用虚构数据的任务：“做一个小工具，在几段资料里查找关键词并告诉我出处。”本实验仅产出规格，不实现工具，不读取或连接 ReflectFlow 数据。

使用上游固定提交 `aeac41d4d005999432bb7312f7ff06383a91d59d` 的 [`spec-driven-development/SKILL.md`](https://github.com/addyosmani/agent-skills/blob/aeac41d4d005999432bb7312f7ff06383a91d59d/skills/spec-driven-development/SKILL.md)。阅读其中的适用条件、六个核心领域、边界和验收要求后，针对以上任务撰写 [SPEC.md](SPEC.md)。本实验中的输入是人为构造的，规格中的具体选择是实验假设，不是用户对正式项目的决定。

## 实际过程

1. 判断该任务是一个可单独验证的“关键词查找”能力，不需要先拆成多模块能力图。
2. 将模糊要求中的不确定之处写成明确假设：命令行、字面匹配、本地虚构资料、最多返回三条等。
3. 按技能的目标、命令、结构、代码风格、测试策略和边界六个方面，写出独立规格；将正确匹配、来源、空结果、错误输入写为可观察的验收条件。
4. 用 [check-spec.py](check-spec.py) 对成品进行结构核对。检查仅验证标题和编号是否齐全，不能证明需求合理或实现正确。

## 结果与观察

原始任务只说明“查找关键词和出处”。成品进一步明确了大小写、匹配方式、结果顺序、无结果提示、文件错误、数据范围及验收用例；它们让后续实施者有了可核验的目标，同时也暴露了“是否要语义搜索、哪种数据格式”等需要真实需求方决定的问题。

```text
python projects/010-agent-skills-engineering-lab/experiment-batch/research/experiments/experiment-spec/check-spec.py
PASS: 8 required sections, 5 acceptance criteria, 3 boundary tiers present
```

上面的检查在本轮实际运行，属于规格文本的格式检查；计划中的原型命令和功能测试尚未执行，因为原型并未实现。本实验没有建立不使用 Skill 的独立对照组，因此不能量化它带来的质量或效率提升，也无法证明技能本身必然使产出更好。

上游技能要求规格产出后等待人工在后续回合审核，再进入规划或实现。本实验只完成了规格阶段；没有声称得到正式项目的人工批准，也没有假装规划和代码已完成。上游文件中的 `Ask first` 属通用建议，实际操作仍受用户明确授权和本仓库约定约束。
