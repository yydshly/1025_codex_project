进阶学习 · 从会用到会创建

把做事经验，变成可重复的能力

学习目标：面对一个新需求，你能设计出 AI 可执行、结果可核对、失败可改进的工作规程。

先通览 25 项的场景，再用一个小能力练完整过程。第一项练习沿用你的真实需求：找回已有研究，提供出处，帮助形成判断。已有回查工具可作为观察材料；下面保留初始教学版本。正式版本与本轮进度请看创建实录。

真实任务→决策与步骤→工具执行→结果验证→失败改进
01 · 定义能力

明确一次要交付什么

把“帮我研究”收窄为“在已登记项目里找出某个库的研究记录，返回结论与出处”。写清输入、输出、允许的数据范围和不适用请求。

你要交出的作业：一页能力契约。验收：仅看它，另一个人也知道什么算完成。

02 · 拆解过程

先观察一次如何做好

跟着真实回查走一遍：识别仓库 → 查登记 → 读来源 → 核对结论 → 交付。特别记录判断点：同名怎么区分、来源不符怎么办、找不到怎样说。

作业：步骤与分支表。验收：每一步都有输入、动作和结果，关键异常有去处。

03 · 写成 Skill

让正确任务找到正确规程

名称与 description 说明“何时用”；正文说明怎么做、产出什么、何时停止。把只在某个分支需要的资料放到 references，使用时再读。

作业：一份简短 SKILL.md。验收：换种提问仍能识别相同目标，不会把无关任务吸进来。

04 · 接入执行

让关键动作有可靠工具

理解、取舍和总结交给模型；固定匹配、格式校验和哈希比对可交给已有代码。确有重复、确定性需求时再加脚本。先确认工具、输入格式和运行环境真实可用。

作业：规则与工具对应表。验收：能解释每条关键规则靠文字提醒、程序检查，还是执行流程阻断。

05 · 独立验证

用没提前讲过答案的任务考试

准备正常、含糊、无匹配、相似名称和证据失效等请求。给新的执行者 Skill 与必要资料，不透露期望结论；观察实际取证和结果。

作业：输入、预期行为、实际证据与失败记录。验收：核对行为和产物，不靠标题或措辞相同判通过。

06 · 迭代与迁移

修正原因，再换任务验证

判断失败来自触发说明、知识不足、步骤缺失、工具缺陷，还是验收薄弱。修最小必要部分，再试未参与修改的新案例；最后迁移到另一类研究资料。

作业：改前／改后证据和适用边界。验收：新案例能独立完成，旧案例没有退步，流程成本值得付出。

练习时重点读这三项，并从上下文组织学习“只加载当前需要的信息”、从独立质疑学习“让不同视角检验判断”。其他技能在对应问题出现时再深入。

迁移要保留判断：审批环节要结合用户现有授权与动作风险；质量阈值要结合实际基线。原库的逐阶段批准和默认百分比不应自动变成你所有任务的固定要求。

深入二：Skill 文件怎样变成实际能力？

宿主先根据名称和 description 考虑是否使用 Skill，再加载正文；模型据此选择动作、调用可用工具，必要时读取辅助资料。Skill 本身不会凭空提供工具、数据访问权或永久记忆。

research-recall/
└── SKILL.md              最小可从这一份文件开始

确有需要时再加：
references/              来源格式、判断规则、条件式细节
scripts/                 可重复的确定性处理与检查
assets/                  交付时使用的模板或素材

文字指导

“每条结论都附出处”改变模型的工作方式，仍可能被遗漏。

程序检查

检查路径存在、引用行和原文一致。只能证明这些条件，不能自动证明结论正确。

流程阻断

执行器接收检查结果：失败就停止生成“完成”状态。CI 要另行配置失败阻断与合并规则。

关键区别：把“必须检查”写进 Skill，并不等于已接上强制门槛。检查脚本存在，也不等于每次执行都会调用。你要能指出实际在哪一步调用，失败后谁阻止继续。

深入三：研究回查 Skill 的初始教学草案

下面是初始教学版本，用来观察如何把经验写成指令；它依赖当前研究总库的登记结构。正式版本见创建实录第 3 步；当前实现与验证状态以实录为准。

---
name: research-recall
description: 在已有研究项目中查找库的用途、适用场景和原文依据；适用于“以前研究过吗”或“当时为什么选择它”等回查请求。
---

## 范围与结果
只检索用户指定或已授权的研究资料范围。
返回：研究记录、来源路径与定位、事实与判断、未确认项。
新的外部调研需要另行确定来源范围，不把它冒充已有记录。

## 执行
1. 从现有上下文提取目标；只有同名歧义影响结果时再澄清。
2. 检查项目登记。对 GitHub 链接使用完整 owner/repo 身份，
   不能把相似前缀当成同一仓库。
3. 阅读匹配项目的来源正文，保留文件、定位与版本信息。
4. 逐条核对结论和原文；区分事实、推断与尚待实测的判断。
5. 无匹配时说明已查范围和“未找到”，不推断“从未研究过”。
6. 保存判断时遵循用户已授权的目的地与方式；
   保存失败或发生冲突时保留原内容，明确报告失败。

## 完成条件
引用可定位，结论有依据；没有把研究记录写成实测结果。
如来源缺失或已变更，标记未核实，不宣称核对完成。

这里体现三种设计：description 控制适用场景；正文控制决策与动作；完成条件控制结果。真正执行仍依赖模型、工具和运行环境。

深入四：怎样验证自己真的学会了？
  • 正常请求：“Agent Skills 研究过吗？”→ 定位真实登记和来源，结论可回查。
  • 不同问法：“之前怎么看这个库？”→ 从上下文识别目标；缺少目标才问，不编造对象。
  • 无匹配：查询快照没有的库 → 明确未找到及范围，不补造记录。
  • 相似名称：查询 agent 的仓库链接 → 不能因前缀相同命中 agent-skills。
  • 来源失效：在隔离样本中移走被引用文件 → 报告不可核实，不能假装完成引用验证。
  • 不适用任务：“帮我写生日祝福”→ 不应启动研究回查流程。

记录任务完成、事实与出处正确、是否遵守边界，以及时间、工具调用和人工补充成本。需要判断 Skill 的增益时，用相同任务、模型和工具比较“有／无 Skill”，多次运行并保留部分未见过的案例；一次成功不足以证明稳定收益。

学会的标志：你能解释每条规则为什么存在，指出实际由什么机制执行，并把这套方法迁移到另一项真实需求。遇到失败时，知道应该改 description、正文、工具还是验证方法。

第一份作业：用五句话定义你自己的“研究回查能力”：什么时候用、允许读哪里、要返回什么、最不能犯什么错、怎样判断完成。这五句话会成为后续 Skill 的设计依据。

编写参考：OpenAI 官方 Skill 编写文档；实现机制对照上述固定版本的上游原文。本节保留通用学习方法与初始教学草案。正式 Skill 的产物、安装和验证情况见上方创建实录。

理解一个 Skill，用这四个问题自查

  1. 何时需要？我能否说出一个具体触发条件？
  2. 改变什么？它约束的是目标、过程、质量，还是交付？
  3. 留下什么？执行后应拿到文档、代码、检查结果，还是运行证据？
  4. 怎样衔接？下一项技能需要接收什么，失败后回到哪里？
