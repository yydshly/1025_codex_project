# Agent Skills：从整体到细节

> 固定版本 aeac41d4d005999432bb7312f7ff06383a91d59d。以下为25项技能的原文解读与教学例子，不是25项实测结论。

## 先看整体

这个仓库将软件工程经验组织成文本工作流程。技能规定适用场景、步骤、检查点和证据；AI助手结合任务与规则调用实际工具，形成文档、代码或运行结果。安装或阅读文本不自动保证质量。

需求 → 规划 → 实现 → 验证 → 审查 → 发布维护，是理解它的主线；调度、上下文、来源、独立质疑、版本、文档和观测可以贯穿其中。分类只是阅读入口，每个任务不必使用全部技能。

## 先分清几组概念

- 需求访谈问清目标；想法细化比较方案；规格写清要做什么；质量约束确定共同底线；规划安排实现步骤。
- 增量实现控制每次工作的范围；测试驱动明确行为；浏览器验证检查实际体验；调试处理已经出现的异常。
- 来源驱动核对外部技术事实；上下文管理组织任务信息；独立质疑审视重要假设；代码审查检查已有变更。
- 代码简化尽量不改变行为；安全关注信任与权限边界；性能优化依赖瓶颈测量。
- 版本记录变更；持续集成自动运行检查；发布控制交付与回退；观测持续收集诊断信息；文档记录原因；迁移管理旧能力退出。

## 用同一个项目贯穿理解

教学场景：做一个只使用虚构材料、返回来源的资料检索小工具。先明确关键词/语义、资料范围和来源要求，再写规格与质量标准；拆分读取、搜索、展示等工作，并设计模块与界面。实现时采用小步、测试与版本记录。遇到结果遗漏就调试，需要验证真实操作就检查浏览器。审查、简化、安全和性能按需要加入；文档和观测随开发推进，交付时用自动检查和发布流程，格式升级时再考虑迁移。该完整产品尚未据此实现，所有单项例子均为教学解释。

## 01 · 技能选择与协作

**阶段：** 调度 · **原名：** `using-agent-skills`

依据任务所处阶段选择技能，并说明多个技能如何接力。它负责指路，不替代具体工作的执行。

### 适用情形

- 不知道当前应先澄清需求、规划、编码还是排错
- 一个功能需要不同工程方法共同完成

### 不必套用的情形

- 把全部 25 项机械地套在每个任务上
- 把它当作自动运行其他技能的独立软件

### 输入

- 用户当前目标和已确认的范围
- 项目现状：有没有规格、实现和验证结果
- 可用工具及项目约定

### 执行步骤

1. 识别当前问题：意图不明、方案待定、实施中、出错或准备发布。
2. 选择最直接相关的技能；必要时组合主技能与专项技能。
3. 明确假设和冲突，保留任务范围，避免无关改造。
4. 完成一个阶段后，将其产出交给下游技能；验证未通过时返回相关环节。

### 产出

- 当前适用的技能及选择理由
- 阶段之间的先后或并行关系
- 每一步需要提供的验证证据

### 原理

它是一张写在文本中的任务分流表。助手据此判断下一步应读取哪份 SKILL.md，模型和宿主工具完成实际调用。它同时规定不凭感觉宣布完成、少做无关改动等共通行为。流程可以回退和并行，不是一条所有任务必走的流水线。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：为虚构资料检索小工具选择工作顺序。

**起点：** 只有一句“帮我做个检索工具”，可能立刻开始选择数据库。

1. 目标不清时先访谈；已确定只查虚构资料时可直接写规格。
2. 规格明确后拆解任务，实施时配合测试。
3. 查不到资料时转入调试；准备交付时再做审查和发布检查。

**预期产物：** 得到一条随任务进展调整的工作路线，而不是同时加载所有技能。

**验证方法：** 检查每次选择是否对应当前问题，以及下游是否拿到了上游的明确产出。

### 边界与配合

- 不能自动提供浏览器、数据库或部署权限。
- 宿主已有原生技能路由时，不宜再把完整元技能长期预加载。
- 上游通用规则必须服从用户要求和项目约定。
- 配合 [规格驱动开发](#spec-driven-development)：将已经清楚的目标转为规格。
- 配合 [系统调试与恢复](#debugging-and-error-recovery)：遇到异常时切换到排错流程。
- 配合 [上下文组织与交接](#context-engineering)：为当前所选流程准备相关上下文。

## 02 · 需求访谈

**阶段：** 需求 · **原名：** `interview-me`

先弄清目标、使用者、成功标准和主要限制，避免把一句模糊要求误解成复杂产品。产出是意图说明。

### 适用情形

- 请求缺少为谁做、为什么做或成功标准
- 简单与灵活、成本与速度等价值取舍尚不明确

### 不必套用的情形

- 解释现有代码等纯信息问题
- 已经明确的改名、格式调整或小修复
- 没有用户响应的定时任务或持续集成环境

### 输入

- 用户原始表达
- 已有项目背景
- 目前仍不确定的目标与限制

### 执行步骤

1. 用一句话写出对用户意图的当前理解，并说明不确定之处。
2. 一次只问一个关键问题，附上自己的猜测，让用户纠正假设。
3. 遇到“要先进、可扩展”等泛泛目标，追问它对应的实际需求。
4. 用用户的语言复述结果、使用者、成功标准、约束和不做的内容。
5. 按上游流程获得明确确认后输出意图说明，再交给后续阶段。

### 产出

- 经确认的意图说明
- 明确的使用者、预期结果和范围边界
- 尚需后续研究的疑问

### 原理

通过一问一答不断更新假设，让需求方纠正助手的理解。它在技术方案出现之前缩小目标范围；上游用约 95% 主观信心作为访谈停止提示，并非经过测量的准确率。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：理解为什么需要虚构资料检索小工具。

**起点：** “想做一个 AI 知识库”可能被解释为上传、向量数据库、问答和自动总结。

1. 先问实际困扰是找不到原文，还是读不懂内容。
2. 假设用户主要想找回原句，再确认资料数量、来源要求和运行环境。
3. 将目标复述为“在少量虚构资料中查关键词，并返回具体出处”。

**预期产物：** 目标从宽泛知识库收敛为可解释的小型查找工具。

**验证方法：** 真正访谈时应由用户确认复述；本示例中的回答是假设，不代表用户已经作出决定。

### 边界与配合

- 不能代替真实用户访谈或市场证据。
- 带猜测的提问可能引导用户，需要允许纠正。
- 上游有严格确认和结束回合规则；实际应用应遵循现有用户授权，避免重复索要确认。
- 配合 [想法细化与方向选择](#idea-refine)：目标明确但实现方向未定时，继续比较方案。
- 配合 [规格驱动开发](#spec-driven-development)：意图足够具体后，转为要求和验收标准。

## 03 · 想法细化与方向选择

**阶段：** 需求 · **原名：** `idea-refine`

先发散出不同做法，再依据用户价值、可行性和差异收敛，形成一个边界清楚的最小方案。

### 适用情形

- 已有大致想法，但尚未选定方向
- 希望比较不同实现路线并暴露假设

### 不必套用的情形

- 连真正目标也不清楚的情况，应先访谈
- 方向已经确定、只差写规格的任务

### 输入

- 大致概念和目标用户
- 成功标准、资源限制和已有尝试
- 现有代码与可复用能力

### 执行步骤

1. 把想法改写为一个具体的问题。
2. 围绕用户、效果、约束和已有尝试提出少量澄清问题。
3. 利用简化、组合、反转或变换受众等角度产生若干有区别的做法。
4. 根据反馈收敛为两到三个方向，比较价值、成本和差异。
5. 列出每个方向依赖的假设与可能失败的原因。
6. 写成一页方案：推荐方向、最小范围、待验证假设和不做事项。

### 产出

- 几个可比较的方案与取舍
- 推荐方向及理由
- 最小可行范围和假设验证清单

### 原理

它先扩大选择空间，再通过明确标准缩小，而不是马上接受最初提出的技术。技能内还提供发想框架和评价参考；价值在于暴露被默认接受的假设，并控制范围。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：选择虚构资料检索工具的第一版方向。

**起点：** 默认认为需要向量检索、聊天和知识图谱一起做。

1. 比较三个方向：关键词定位、语义检索、问答生成。
2. 按“能否找到原文、依赖数量、维护成本”评估。
3. 假设资料很少且强调出处，先选关键词定位，把语义检索留作后续对照。

**预期产物：** 形成一页方案，并明确暂不做生成回答或复杂建图。

**验证方法：** 检查推荐是否回应用户目标，关键假设有没有低成本验证方式；示例未进行实际方案对照。

### 边界与配合

- 生成多个想法不等于验证用户需求或商业价值。
- 推荐仍受输入信息与助手判断影响。
- 不能把讨论中的假设写成已证实结论。
- 配合 [需求访谈](#interview-me)：意图不清时先回到需求访谈。
- 配合 [规格驱动开发](#spec-driven-development)：选定方向后把方案写成可验收规格。
- 配合 [独立质疑](#doubt-driven-development)：对已经形成的重要方案进一步独立质疑。

## 04 · 规格驱动开发

**阶段：** 需求 · **原名：** `spec-driven-development`

把方向转换为具体行为、运行命令、结构、测试和边界，让开发与验收依据同一份说明。

### 适用情形

- 新功能或较大改动尚无明确规格
- 一个请求包含多个可以独立验证的能力

### 不必套用的情形

- 明确的单行修复或错别字更正
- 已有合适规格体系时另建一份重复文档

### 输入

- 已明确的目标和选定方案
- 现有技术栈、目录、命令与代码约定
- 项目约束和待解决问题

### 执行步骤

1. 先判断是否包含多个独立能力；必要时画模块、依赖和构建顺序。
2. 显式列出假设，补清目标用户、范围和成功条件。
3. 写明目标、完整运行命令、项目结构、代码风格、测试策略和行为边界。
4. 把“好用、快速”等抽象要求变成可观察条件，保留未决问题。
5. 按上游阶段流程审核规格，再进入方案、任务和实施；已有授权和项目规则优先。
6. 需求改变时同步更新规格，使它继续对应实际功能。

### 产出

- 需求规格或现有规格系统中的对应文档
- 可测试的验收条件
- 复杂请求的能力地图及模块边界

### 原理

它把自然语言要求转换成开发者和验收者共同使用的契约。能力地图先划分独立功能，后续规划再拆分实现任务，避免把模块划分和任务顺序混在一起。文档本身不执行测试。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：定义虚构资料检索工具第一版。

**起点：** “能搜索资料”没有说明匹配方式、出处和空结果行为。

1. 约定输入是虚构文本资料，第一版使用字面关键词匹配。
2. 明确输出包含原句和资料编号，空结果显示无匹配，不补造回答。
3. 给出普通查询、空输入、缺失资料文件等验收条件。

**预期产物：** 开发者可以按同一份规格实现，验收者可以按条件逐项检查。

**验证方法：** 能否为每条关键要求构造输入与预期输出；这段是教学示例，现有规格实验另有独立记录。

### 边界与配合

- 规格完整不代表需求正确，仍需实际验证和反馈。
- 严格阶段审核是上游的流程偏好，不自动覆盖当前授权。
- 大功能应分模块，小任务不必写冗长文档。
- 配合 [规划与任务拆解](#planning-and-task-breakdown)：把规格拆成依赖有序的实施任务。
- 配合 [质量约束与检查门槛](#constraint-driven-development)：补充适用于所有任务的共同质量要求。
- 配合 [接口与契约设计](#api-and-interface-design)：模块边界需要明确接口契约。

## 05 · 质量约束与检查门槛

**阶段：** 需求 · **原名：** `constraint-driven-development`

把质量标准写成项目长期规则，并为每条可检查的标准指定命令、执行时机和失败处理，防止通过降低标准掩盖问题。

### 适用情形

- 项目没有明确质量底线
- 已有检查却不清楚哪些会阻止交付
- 经常跳过测试或关闭检查来获得通过结果

### 不必套用的情形

- 已有约束且无需修改时重新访谈
- 一次性探索脚本套用完整生产门槛
- 把上游默认阈值当作所有项目必须达到的数字

### 输入

- 项目当前的测试、类型检查、扫描和构建配置
- 实际测量基线
- 用户关心的质量维度和可接受的检查成本

### 执行步骤

1. 先读现有配置和基线，只询问资料无法回答的质量取舍。
2. 明确检查维度、阻止或提示方式、目标数值与耗时预算。
3. 记录到 CONSTRAINTS.md，注明每条规则的原因、命令和执行阶段。
4. 接入合适的已有工具，区分快速编辑检查、任务检查和持续集成检查。
5. 复核变更是否降低阈值、删测试、加忽略标记或留下未实现部分。
6. 暂不适合绝对目标时记录现状并要求不退步；例外应有负责人和期限。

### 产出

- 可持续使用的质量约束文档
- 能实际运行的检查命令和执行时机
- 有依据的基线、例外和结果记录

### 原理

将“要高质量”拆成有判定方式的条件。书面规则靠助手遵循；接入脚本或持续集成后才有机械检查。它还检查规则本身是否被放宽，并区分外部工具、项目规则和自写测试这三类证据。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：给虚构资料检索工具设定共同底线。

**起点：** 每次都说测试通过即可，但测试可以被跳过，出处也没有固定要求。

1. 规定已有检查不能被无理由删除，错误输入必须有明确反馈。
2. 为代码检查和行为测试分别指定实际命令。
3. 如果以后有网页，再按真实测量设置可访问性或性能目标，而不凭空填写分数。

**预期产物：** 后续每个功能都知道必须通过什么检查以及在哪里执行。

**验证方法：** 每一条数字或硬要求是否对应可运行的判定机制；是否能发现通过改标准让结果变绿。

### 边界与配合

- 文件存在不等于已经强制执行，工具需要正确安装和配置。
- 默认覆盖率和性能数字是上游建议，需要按项目与基线调整。
- 检测工具和测试都有覆盖边界，不能证明没有缺陷。
- 配合 [测试驱动开发](#test-driven-development)：行为测试提供一部分质量证据。
- 配合 [持续集成与自动化](#ci-cd-and-automation)：在自动流程中运行这些约束。
- 配合 [代码审查与质量判断](#code-review-and-quality)：审查既看代码，也检查是否偷改质量底线。

## 06 · 规划与任务拆解

**阶段：** 规划 · **原名：** `planning-and-task-breakdown`

将规格拆成依赖有序、可单独验证的小任务。强调每次交付一段完整用户流程，而不是先把所有底层都做完才连接界面。

### 适用情形

- 有规格但任务太大，不知道从何开始
- 需要确定依赖和可并行工作
- 跨会话协作需要保存进度

### 不必套用的情形

- 单文件且范围明显的修改
- 已有清晰任务清单时重复拆解

### 输入

- 规格和验收条件
- 相关源码与既有模式
- 当前未完成计划和工作状态

### 执行步骤

1. 只读了解规格、现有代码、风险和未知项。
2. 画出组件依赖，明确哪些基础必须先完成。
3. 按完整可用行为切片，而不是按数据库、接口、界面各做一大批。
4. 为每项任务写目标、验收条件、验证方式、依赖与可能修改的文件。
5. 优先处理高风险，安排检查点，并区分可并行与必须顺序的任务。
6. 保存计划与任务状态，保留已有未完成工作，不随意覆盖。

### 产出

- 实施计划，默认 tasks/plan.md
- 任务清单，默认 tasks/todo.md 或指定跟踪系统
- 依赖顺序、验证点和风险说明

### 原理

用可验证的小单元限制每次工作的范围，并通过依赖关系防止并行冲突。计划承接规格的“要什么”，回答“分几步怎样实现”；每个切片都应能运行或被检查，而不是留下长期半成品。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：安排虚构资料检索工具的实施顺序。

**起点：** 任务清单只有“写后端、做前端、完成测试”。

1. 第一步完成单条资料的关键词查询和出处输出。
2. 第二步扩展多资料与空结果行为，并复用第一步测试。
3. 第三步处理错误文件和非法输入；如需网页，先定查询契约再并行做页面。

**预期产物：** 每一步都有可观察结果，且能指出哪些任务依赖已有能力。

**验证方法：** 任务是否有明确验收与验证方式，完成一项后是否仍能运行；不能仅以文件数量判断切片合理。

### 边界与配合

- 计划和估计不保证实际工作量。
- 文件数、任务时长属于经验指引，需要结合工程情况。
- 不能覆盖其他会话尚未完成的计划，或擅自关闭跟踪项。
- 配合 [规格驱动开发](#spec-driven-development)：规划需要明确规格作为输入。
- 配合 [增量实现](#incremental-implementation)：实施技能按任务逐步执行。
- 配合 [上下文组织与交接](#context-engineering)：每一项任务只加载相关资料，并保存交接状态。

## 07 · 增量实现

**阶段：** 实现 · **原名：** `incremental-implementation`

把实现工作拆成可独立运行和检查的小块，每块完成后再继续；重点在执行节奏，而不是再写一份任务清单。

### 适用情形

- 需求已经明确，要实施涉及多个文件的功能
- 一次改动过大，难以定位错误或回退
- 功能尚未全部完成，需要隐藏未准备好的部分

### 不必套用的情形

- 范围已经很小的单函数改动
- 需求仍不清楚、尚未决定要做什么

### 输入

- 已经明确的功能目标和验收条件
- 有先后顺序的任务及本次范围
- 现有代码、测试与构建命令

### 执行步骤

1. 选择最小但完整的一条用户路径；也可先验证最高风险，或先定义前后端契约。
2. 只实现这一块，保持现有系统可运行，不顺手加入其他功能或改造。
3. 运行与改动有关的测试、构建和必要的真实操作检查。
4. 通过后保存可追溯的进度，再进入下一块；上游建议按逻辑单元提交，实际遵循项目授权。
5. 对未完成的能力使用适当的关闭默认值或开关，并考虑每块如何回退。

### 产出

- 逐块可运行的功能与验证记录
- 范围清楚、便于审查和回退的变更
- 哪些部分已完成、哪些仍未开放的说明

### 原理

它把错误反馈提前到每个小块结束时。优先按用户能走通的路径切分，而非先把所有数据库、所有接口、所有页面分别堆完；也允许契约优先和风险优先。小范围变更有助于缩小排查范围，但只是流程纪律，Skill 不会自动执行提交或生成回滚机制。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：为虚构资料检索小工具逐步增加关键词搜索和来源查看。

**起点：** 打算一次加入导入、语义检索、筛选、分页和原文阅读，任何一处出错都很难判断原因。

1. 第一块只让用户输入关键词并看到一条真实匹配的虚构资料。
2. 第二块加入出处和打开原文，检查搜索到原文的完整路径。
3. 第三块再加无结果提示与筛选；每块都验证此前行为仍然可用。

**预期产物：** 预期得到分阶段可体验的功能，以及每阶段对应的验证记录；不是一次性宣称整个产品已完成。

**验证方法：** 每块都能回答：用户现在能完成什么、执行了哪些检查、失败时能退回哪里。

### 边界与配合

- 过度拆分也有沟通和集成成本，应按逻辑完整性切分。
- 小步提交不等于每一步都具备可靠回滚，尤其不能据此推断数据迁移安全。
- 上游约一百行等规模建议是提醒，不是本项目的机械指标。
- 配合 [规划与任务拆解](#planning-and-task-breakdown)：规划先决定做哪些块，增量实现负责逐块完成。
- 配合 [测试驱动开发](#test-driven-development)：每个小块内部可用测试先明确行为。
- 配合 [Git 工作流与版本](#git-workflow-and-versioning)：版本管理让完成的进度可追溯。

## 08 · 测试驱动开发

**阶段：** 实现 · **原名：** `test-driven-development`

先写一个表达预期行为且会失败的测试，再做最小实现使它通过，最后整理代码并继续检查。修复故障时先用测试复现。

### 适用情形

- 新增或改变逻辑行为
- 修复可复现的错误
- 补足空输入、边界值或异常行为

### 不必套用的情形

- 不改变行为的纯文档或静态内容调整
- 仅为了凑测试数量，重复实现逻辑的检查

### 输入

- 预期输入与输出、需要保持的旧行为
- 项目实际使用的测试框架和命令
- 可隔离的样例数据与必要依赖

### 执行步骤

1. 先查项目如何运行测试，区分单项检查与完整测试，不默认套用某个命令。
2. 写出描述用户可观察行为的测试，运行并确认它因目标问题而失败。
3. 实现足够让该行为通过的最少代码，不提前扩展无关需求。
4. 测试通过后整理命名或结构；每次改变后确认行为保持不变。
5. 按风险补充边界和集成检查；浏览器功能还需真实运行验证。

### 产出

- 预期行为的可执行用例
- 修复前失败、修复后通过的证据
- 可在后续修改时重跑的回归检查

### 原理

先观察失败，可以确认用例确实能识别目标缺陷，减少为了既有代码编写‘必然通过’的测试。它强调检验结果而非内部调用顺序，并优先使用真实实现或简单内存替代；单元、集成和端到端检查分别覆盖不同层次。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：让虚构资料检索小工具正确处理空关键词。

**起点：** 空字符串可能意外匹配全部资料，但没有明确规则，也没有自动检查。

1. 先约定空白关键词不发起检索，并返回‘请输入关键词’。
2. 写测试传入空格，确认现有实现没有符合约定。
3. 添加输入处理，再运行正常匹配、无匹配和空白输入检查。
4. 调整内部代码时保持这些结果不变。

**预期产物：** 预期得到实现代码和一组可重跑的行为用例；需求是否合理仍需单独判断。

**验证方法：** 人为撤回这项处理时，相关用例应失败；恢复后通过，其他已验证行为不受影响。

### 边界与配合

- 测试通过只说明所测场景满足断言，不证明没有其他错误。
- 上游的测试比例和普遍 TDD 偏好是方法建议，应结合项目风险与成本。
- 过度模拟依赖可能让测试通过而实际集成失败；测试本身也可能写错。
- 配合 [规格驱动开发](#spec-driven-development)：规格提供期望行为，测试将部分验收条件转为可执行检查。
- 配合 [系统调试与恢复](#debugging-and-error-recovery)：调试找到问题后，用回归用例防止同类错误再次出现。
- 配合 [浏览器运行验证](#browser-testing-with-devtools)：函数测试不能代替实际浏览器中的布局与交互验证。

## 09 · 上下文组织与交接

**阶段：** 实现 · **原名：** `context-engineering`

分层组织项目规则、规格、源码、错误和进度，减少信息不足、过多或过时导致的误解，并为跨会话继续工作留下记录。

### 适用情形

- 新会话或切换功能模块
- 助手忽略约定、重复已有功能或引用不存在的接口
- 长任务需要压缩信息或交接

### 不必套用的情形

- 把全仓内容和全部技能一次性塞入提示
- 把上下文整理当作训练模型或永久记忆系统

### 输入

- 项目规则和当前任务
- 相关规格、源码、测试与既有实现示例
- 本轮错误、已验证结果和未解决问题

### 执行步骤

1. 将长期规则、功能规格、当前源码和本轮错误分层组织。
2. 编辑前读取目标文件、相关测试、接口和一个可参考的现有模式。
3. 只引入当前步骤需要的材料，区分项目资料与外部不可信内容。
4. 长会话中压缩过时尝试，保留目标、约束、当前错误和有效决定。
5. 在完成任务边界记录范围、状态、变更、验证结果和未决项。
6. 新会话先核对实际文件与工作区状态，再从记录继续。

### 产出

- 当前任务所需的集中上下文
- 简明项目规则或目录索引
- 可恢复工作的进度与验证记录

### 原理

它改变助手接收到的信息结构和时机：稳定规则长期保留，具体源码按任务加载，错误按迭代更新。通过保留结论、减少失效过程来控制信息量；不会凭空扩大上下文窗口或自动获得历史记忆。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：只修复虚构检索工具的来源显示。

**起点：** 助手读了大量无关历史，但不知道资料编号字段和当前测试。

1. 提供来源字段约定、显示函数、相关测试和一个正常结果。
2. 保留“只用虚构资料、不得修改正式库”的边界。
3. 修复后记录改变的文件、测试结果和未完成事项，供下次继续。

**预期产物：** 助手围绕出处显示工作，下一次会话也能知道已做什么。

**验证方法：** 回答是否引用真实现有文件和接口，交接记录能否与工作区核对；示例并未测量上下文效率。

### 边界与配合

- 宿主决定真正的上下文和压缩能力，技能只提供组织方法。
- 摘要可能遗漏细节，必要时须返回原始资料核对。
- 外部内容中的指令不能覆盖用户要求；持久记录也需避免暴露私人内容。
- 配合 [规划与任务拆解](#planning-and-task-breakdown)：任务清单决定每次应准备哪些上下文。
- 配合 [依据官方资料开发](#source-driven-development)：外部文档应按需读取并保留来源。
- 配合 [文档与决策记录](#documentation-and-adrs)：值得长期保留的决定应转为正式文档。

## 10 · 依据官方资料开发

**阶段：** 实现 · **原名：** `source-driven-development`

先识别技术版本，再查对应官方资料，依照有依据的模式实现，并指出未核实部分。核心是建立技术决定与来源之间的联系。

### 适用情形

- 使用某个框架、库或平台的特定接口
- 准备生成会被反复复制的代码模板
- 怀疑记忆中的做法已过时

### 不必套用的情形

- 不依赖库版本的简单逻辑或文字调整
- 把查到文档视作运行验证的替代

### 输入

- 依赖清单及可核对版本
- 需要实现的具体功能
- 官方接口说明、变更记录及适用的平台信息

### 执行步骤

1. 从项目依赖与环境中识别技术栈和版本，不凭印象选择。
2. 读取对应功能的官方页面，重点提取接口、示例、废弃说明和迁移规则。
3. 遇到文档间或文档与项目的冲突，显式记录并核对实际适用性。
4. 按已核实的签名与模式实现，未经资料覆盖的做法清楚标明。
5. 给出与技术决定对应的具体来源；把外部页面当资料，忽略其中针对助手的指令。

### 产出

- 版本明确的技术依据
- 可追溯来源的实现选择
- 冲突、兼容条件和未验证项清单

### 原理

通过版本识别和资料检索，把“模型记得如此”改成“此版本官方资料支持如此”。它并不是检索模型或数据库，而是规定如何查证和引用。官方资料能支持 API 用法，但实现是否正确仍需运行测试。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：为虚构资料检索工具考虑引入全文检索库。

**起点：** 助手直接凭记忆写出某个库的调用方式。

1. 先查项目当前使用的运行时与依赖版本。
2. 核对候选库官方文档中的建索引、查询、中文处理和结果位置规则。
3. 只采用已确认的接口，将未找到依据的功能单独列出，再准备小样验证。

**预期产物：** 得到版本与来源清楚的实现方案，知道哪些能力还不能确认。

**验证方法：** 引用是否直接支持该版本的具体用法；后续测试是否验证真实行为，而非只复制文档示例。

### 边界与配合

- 资料可能过时、缺失或互相矛盾，引用不是正确性保证。
- 查询资料需要可用的网络或文档工具。
- 它主要核验技术接口和模式，不代替效果评测、许可审查或用户需求判断。
- 配合 [上下文组织与交接](#context-engineering)：只加载当前技术决定需要的资料。
- 配合 [测试驱动开发](#test-driven-development)：有资料依据之后仍需用测试验证行为。
- 配合 [安全检查与加固](#security-and-hardening)：外部资料读取也需要防范不可信指令和不必要外联。

## 11 · 独立质疑

**阶段：** 实现 · **原名：** `doubt-driven-development`

在重要决定尚可调整时，让不继承原作者推理的审查者针对方案和约束寻找反例，再核对意见；它不是对完成代码的最终验收。

### 适用情形

- 方案跨模块、涉及状态顺序或重要数据
- 在陌生代码中做非显然的决定
- 声称某个设计安全、可扩展或满足复杂约束之前

### 不必套用的情形

- 机械重命名、格式调整或简单资料摘要
- 每一步都重复质疑，导致无法推进
- 把审查者的意见直接当成权威结论

### 输入

- 需要检验的具体方案、代码片段或结论
- 必须满足的行为契约和必要事实
- 能够独立读取材料的审查环境

### 执行步骤

1. 写清正在依赖什么判断，以及判断错误会带来什么影响。
2. 提取最小可审查材料和约束，去掉作者的说服过程与结论导向。
3. 请独立视角寻找未明说的假设、边界条件和失败路径，而不是询问‘是否不错’。
4. 重新对照原文，把意见分为契约误读、有效可修复问题、可接受取舍和误报。
5. 只针对有效问题调整；出现重复或轻微反馈时停止，上游最多三轮后需重新评估。

### 产出

- 经过核对的问题清单与处理决定
- 补充后的约束或修订方案
- 剩余取舍、未解决问题和停止原因

### 原理

通过不传递作者结论的独立上下文，尝试减少‘顺着原有思路证明自己正确’的偏差。核心是明确契约、寻找反例、逐条核对，而不是增加审查人数；缺少上下文的审查者也会误判。上游还描述可选择的跨模型复核，其授权与工具条件需另行满足。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：审视虚构资料检索小工具的索引更新方案。

**起点：** 方案声称‘每天重建索引就不会漏资料’，却没有说明更新中断或旧资料修改时怎么办。

1. 交给独立视角：索引生成方案，以及‘更新失败仍可查旧资料’等约束。
2. 要求寻找更新中途失败、重复导入、相同 ID 内容改变等反例。
3. 逐项核对，补充索引切换条件和失败处理；对不适用的意见说明原因。

**预期产物：** 预期得到更明确的方案和待验证情形；这仍不是实际证明索引安全的测试结果。

**验证方法：** 每个采纳的意见都应对应方案变化或测试条件；没有证据的意见不自动算缺陷。

### 边界与配合

- 同类模型可能共享盲点，独立上下文也不保证正确。
- 没有独立审查环境时只能自我检查，不能称为独立复核。
- 跨模型会增加时间与成本；上游的交互规则不自动覆盖用户授权或本项目要求。
- 配合 [依据官方资料开发](#source-driven-development)：来源驱动核对外部事实，独立质疑核对我们如何使用这些事实。
- 配合 [代码审查与质量判断](#code-review-and-quality)：独立质疑可发生在设计中途，代码审查更关注完成变更的质量。
- 配合 [测试驱动开发](#test-driven-development)：可执行的反例能进一步变成行为测试。

## 12 · 前端界面工程

**阶段：** 实现 · **原名：** `frontend-ui-engineering`

指导组件结构、状态归属、设计一致性、响应式和可访问性，让实现围绕真实内容与操作，而不只生成一张正常状态的页面。

### 适用情形

- 新建或修改网页、界面组件
- 处理加载、空结果、错误或权限状态
- 改善窄屏显示、键盘操作和界面一致性

### 不必套用的情形

- 只修改后台逻辑且不影响界面
- 把设计偏好当成所有项目都必须遵守的视觉模板

### 输入

- 页面要帮助用户完成的任务和主要操作
- 项目已有的颜色、间距、字体和组件规范
- 真实长度的示例内容及各类交互状态

### 执行步骤

1. 先明确页面任务，参考已有设计或相关界面，写清主要操作和必须覆盖的状态。
2. 按职责组织组件，分开数据获取与展示，选最简单够用的状态管理方式。
3. 实现加载、成功、空结果、错误等实际会出现的状态，并提供可理解的反馈。
4. 使用语义化控件、可见标签和合理焦点顺序，支持键盘与辅助阅读。
5. 在不同屏幕宽度检查内容、布局、交互和项目设计规范的一致性。

### 产出

- 可操作的页面与职责明确的组件
- 覆盖多种状态的界面及行为说明
- 响应式与可访问性检查记录

### 原理

它通过组件职责、状态分类和界面验收清单，让助手考虑正常画面之外的情况。例如筛选值可以放到 URL，局部弹窗状态留在组件，而不把所有状态都放到全局；它也要求用实际内容检查排版。视觉质量来自设计选择与检查，Skill 自身没有渲染或审美评分引擎。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：为虚构资料检索小工具设计搜索页。

**起点：** 页面只有输入框和结果卡片，没有说明加载中、零结果或资料读取失败。

1. 明确主要路径：输入关键词、浏览结果、打开来源。
2. 补齐正在查找、未找到、读取失败和正常结果状态。
3. 给输入框加可见标签，为来源按钮提供清楚文字，检查键盘焦点。
4. 用长标题和窄屏检查换行、横向溢出和操作位置。

**预期产物：** 预期得到在多种状态下都可理解的搜索界面，而不是只有正常结果的效果图。

**验证方法：** 用户不用鼠标也能搜索并打开来源；空结果和错误可区分，窄屏内容不遮挡操作。

### 边界与配合

- 上游的颜色、组件规模等意见是设计指导，不能机械套用到所有产品。
- 文中的 React 等代码只是示例，不代表必须改用该框架。
- 有标签和对比度检查不等于完整无障碍合规认证。
- 配合 [接口与契约设计](#api-and-interface-design)：清楚的数据与错误契约决定页面能显示哪些状态。
- 配合 [浏览器运行验证](#browser-testing-with-devtools)：将设计和代码放进真实浏览器验证。
- 配合 [性能测量与优化](#performance-optimization)：界面完成后，用测量判断是否存在加载或交互瓶颈。

## 13 · 接口与契约设计

**阶段：** 实现 · **原名：** `api-and-interface-design`

先定义模块之间的约定，再实现内部逻辑；统一输入、返回、错误和兼容规则，也考虑有副作用操作在重试时会发生什么。

### 适用情形

- 设计接口、模块函数、组件参数或前后端边界
- 多个实现者需要并行工作
- 改变已有公开行为或增加可重试的写操作

### 不必套用的情形

- 为了简单单文件工具而强行引入远程 API
- 只给字段起名字，却不定义具体行为和错误条件

### 输入

- 调用方需要完成的操作与约束
- 输入来源、数据类型及可信边界
- 已有使用者依赖的行为和兼容要求

### 执行步骤

1. 定义输入、输出及每种结果的含义，先形成可讨论的契约。
2. 在外部输入进入系统的边界校验数据，统一错误格式和处理规则。
3. 明确排序、分页、过滤、缺失字段等可观察行为，避免暴露无意维护的内部细节。
4. 修改接口时优先兼容扩展，评估旧调用方对显性及隐性行为的依赖。
5. 若操作改变状态，明确重试、重复请求和结果未知的处理；需要幂等时验证其实际实现。

### 产出

- 可查阅的输入输出定义、错误约定和示例
- 兼容及重试行为说明
- 用于不同模块对接的契约检查

### 原理

它把隐含约定变成可检查的边界。调用方不应猜测失败时得到空值、异常还是错误对象；设计也要考虑用户可能依赖未写明的排序等行为。对于写操作，声明支持重复请求保护还不够，必须有稳定标识、原子占用和结果记录等机制，这些都需要真正实现。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：定义虚构资料检索小工具中查询模块与页面之间的接口。

**起点：** 页面不知道空关键词如何处理，检索模块有时返回数组、有时返回字符串错误。

1. 约定输入包含关键词与结果数量上限，成功结果包含文档 ID、片段和出处。
2. 区分合法的零条结果与资料读取失败，规定一致的错误表示。
3. 明确结果排序和出处格式，让页面与检索逻辑能够分别实现并对接。

**预期产物：** 预期得到一份能驱动实现和测试的接口约定；这个简单只读查询不需要凭空加入支付式幂等架构。

**验证方法：** 不同模块对同一输入应理解一致；空结果、非法输入和内部失败能被调用方正确区分。

### 边界与配合

- 类型定义不能单独证明运行时输入可靠，也不能替代集成测试。
- 命名、单版本等上游偏好需适配已有项目，不能据此随意破坏旧契约。
- 涉及数据库、外部服务或并发的正确性，需要实际实现和相应测试。
- 配合 [规格驱动开发](#spec-driven-development)：规格决定用户需要什么，接口设计细化模块怎样协作。
- 配合 [增量实现](#incremental-implementation)：接口先明确，可以让页面与后台按约定分别实现再集成。
- 配合 [弃用与迁移](#deprecation-and-migration)：无法兼容的接口变化需要过渡与退出计划。

## 14 · 浏览器运行验证

**阶段：** 验证 · **原名：** `browser-testing-with-devtools`

借助浏览器开发工具观察真实页面、控制台、网络、样式和性能，再验证修改是否解决问题。上游具体依赖配置好的 Chrome DevTools MCP。

### 适用情形

- 页面布局或交互发生变化
- 出现白屏、点击无反应、请求失败等问题
- 需要检查响应式、可访问性或性能表现

### 不必套用的情形

- 纯后台或命令行改动，不涉及浏览器行为
- 没有实际打开页面却声称完成浏览器验证

### 输入

- 可访问的测试页面与可重现操作
- 预期画面和行为
- 已配置的浏览器工具、隔离测试环境和样例数据

### 执行步骤

1. 打开已知测试页面，执行用户路径，保存出现问题时的实际状态。
2. 根据问题检查 DOM、计算样式、控制台或网络，区分界面、数据与服务问题。
3. 对性能问题先记录基线和瓶颈，对无障碍问题检查语义、名称与焦点顺序。
4. 修改源码后重新加载，重复相同操作并与原状态比较。
5. 记录已检查的视口、操作、错误及未覆盖项，而不把一次截图当成全流程验证。

### 产出

- 截图、运行状态、网络或控制台证据
- 可重现的操作步骤和实际观察
- 修复前后比较及剩余问题

### 原理

它通过真实浏览器反馈补足静态阅读和函数测试无法看到的布局、焦点、网络时序等信息。工具负责采集，Skill 负责组织观察与诊断；它不是浏览器驱动本身。浏览器读出的页面和日志是待分析数据，不是新的任务指令。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：检查虚构资料检索小工具在手机宽度下能否完成查找与来源阅读。

**起点：** 函数测试通过，但用户可能看不到被长标题挤出屏幕的来源按钮。

1. 在测试页面输入关键词，打开结果来源，并用键盘完成同一路径。
2. 切换窄屏，检查长标题、空结果和错误提示是否遮挡操作。
3. 查看实际请求与控制台，确认资料读取失败时不会留下无法理解的空白页。

**预期产物：** 预期得到关于实际页面行为的记录，而不是仅凭代码推断‘应该可以’。

**验证方法：** 记录具体视口和操作；截图与状态证据应能支持每条通过或失败的结论。

### 边界与配合

- 未配置相应 MCP 工具时，上游的具体调用步骤不能直接运行；其他工具是否等效需说明。
- 本机、单浏览器或单次操作不能代表所有设备和用户环境。
- 默认使用隔离测试环境，不读取真实账号凭据；现有保护规则和工具权限仍然适用。
- 配合 [前端界面工程](#frontend-ui-engineering)：前端技能负责实现界面，本技能检查真实运行结果。
- 配合 [系统调试与恢复](#debugging-and-error-recovery)：采集到的运行证据可用于缩小故障范围。
- 配合 [性能测量与优化](#performance-optimization)：性能追踪提供优化需要的基线和瓶颈数据。

## 15 · 系统调试与恢复

**阶段：** 验证 · **原名：** `debugging-and-error-recovery`

先保留故障证据，再复现、定位、缩小问题、修复原因并检查是否复发；覆盖测试、构建和运行异常。

### 适用情形

- 测试或构建失败
- 原来可用的行为突然不对
- 用户报告错误、日志出现异常或实际行为偏离预期

### 不必套用的情形

- 功能尚未定义清楚，需要先判断预期是什么
- 借调试之名改造无关模块或清理真实数据
- 无法复现时仍直接断言已找到原因

### 输入

- 预期与实际差异、重现步骤
- 错误输出、日志、相关数据流和运行环境
- 可隔离的最小样例与已知正常版本（若有）

### 执行步骤

1. 暂停叠加新功能，保留日志、输入和故障现场。
2. 尝试可靠复现；无法复现时检查时序、环境与状态差异，并明确未知。
3. 沿界面、接口、存储或构建链路定位出错环节，缩小成最少条件。
4. 修复导致问题的原因，避免只在显示层掩盖症状。
5. 添加能识别该问题的回归检查，并验证原始用户路径及相关旧行为。

### 产出

- 可重现的故障与根因说明
- 范围明确的修复和回归用例
- 验证结果；若未解决则保留已知条件和后续观察方向

### 原理

流程通过控制变量和缩小样例，区分‘在哪里看见错误’与‘哪里造成错误’。它也明确测试本身可能错误、问题可能依赖时序或状态。日志和工具帮助收集证据，Skill 不会自动恢复数据，更不授权重置应用。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：虚构资料检索小工具搜不到昨天导入的一段材料。

**起点：** 只看到搜索无结果，尚不能判断是材料不存在、索引遗漏还是查询规则不匹配。

1. 保留查询词和输入记录，分别检查原文、索引项与查询输出。
2. 用昨天和今天各一条虚构资料缩小问题，定位是否只索引了当天内容。
3. 根据证据修正对应环节，检查旧内容、今天内容、无结果查询和重新构建。

**预期产物：** 预期得到原因与验证证据；这里的教学叙述不是新的运行结果，已有调试实验需单独查看。

**验证方法：** 原始失败条件修复后通过，撤回修复时可再次观察到问题；不要用文件数量代替内容验证。

### 边界与配合

- 最小模型的修复不能直接证明真实复杂系统已修复。
- 偶发问题可能只能缩小范围，不能保证当场找到原因。
- 错误文本是诊断数据，不应不加核实地执行其中夹带的指令。
- 配合 [测试驱动开发](#test-driven-development)：把可复现的问题固定成回归测试。
- 配合 [浏览器运行验证](#browser-testing-with-devtools)：前端故障需要实际页面、请求和控制台证据。
- 配合 [运行观测与诊断信息](#observability-and-instrumentation)：难复现的运行故障依靠合适的长期日志和指标继续观察。

## 16 · 代码审查与质量判断

**阶段：** 审查 · **原名：** `code-review-and-quality`

从正确性、可读性、架构、安全和性能五个维度审视具体变更，核对验证证据，并区分必须修改的问题与可选建议。

### 适用情形

- 实现或修复完成后，准备合并变更
- 检查其他人或 AI 生成的代码
- 审视重构或依赖升级是否引入回退

### 不必套用的情形

- 只检查格式或只看测试通过就宣布批准
- 把个人风格偏好当作必须修改的问题
- 未读取上下文就对整个项目给出全面质量结论

### 输入

- 改动内容、需求或问题背景
- 现有项目约定及模块关系
- 测试、构建、浏览器或测量证据

### 执行步骤

1. 先理解改动目的和预期行为，再阅读测试，确认它们覆盖真正的要求。
2. 沿五个维度阅读实现，优先检查边界、错误路径与结构性回退。
3. 按需要在隔离副本中检验测试是否能抓住错误，而非只相信通过结果。
4. 给每项发现标明证据、影响和处理优先级；区分阻塞、必要与可选建议。
5. 核对修订后的验证记录，给出针对本次范围的判断和未覆盖部分。

### 产出

- 有证据和优先级的问题清单
- 可操作的修正建议与审查结论
- 测试覆盖不足、结构风险或剩余取舍的说明

### 原理

五个维度把‘看起来不错’拆成可具体检查的问题。先读测试可看懂意图，但还要核验用例是否真的会在行为错误时失败；对结构问题应提出如何减少复杂性，而不只要求换一种写法。它关注完成变更的整体健康，和开发中途的独立质疑互补。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：审查虚构资料检索小工具新增的结果导出功能。

**起点：** 作者只说‘导出成功，测试通过’，没有说明空结果、文件失败或来源字段如何处理。

1. 先读需求和测试，确定导出必须保留出处且不能改变原始资料。
2. 检查字段验证、错误返回、模块职责和结果数量限制。
3. 针对确定的风险补充证据；把真实行为缺陷与命名偏好分开。

**预期产物：** 预期得到针对这次改动的审查记录；没有发现问题也只代表检查范围内未发现。

**验证方法：** 每个重要问题都能指出具体触发条件和受影响行为；批准不能只依靠代码作者的自述。

### 边界与配合

- 五维清单不是完整安全审计或性能基准。
- 上游对提交规模、回复时限的建议服务于团队协作，应结合本项目。
- 变异检查等操作必须在安全范围中进行；审查无发现不等于代码不存在缺陷。
- 配合 [独立质疑](#doubt-driven-development)：前者在过程中挑战假设，本技能对完成变更做综合审查。
- 配合 [安全检查与加固](#security-and-hardening)：安全维度发现重要问题后，需进入更深入的安全检查。
- 配合 [代码简化](#code-simplification)：审查发现复杂结构后，可按保持行为的方式专门简化。
- 配合 [质量约束与检查门槛](#constraint-driven-development)：项目约束提供事先约定的质量底线，避免审查时临时改标准。

## 17 · 代码简化

**阶段：** 审查 · **原名：** `code-simplification`

保持输入、输出、错误处理和执行顺序不变，让代码更容易理解和维护。目标是清晰，不是行数最少。

### 适用情形

- 功能已工作，但存在深层嵌套、重复条件或职责混杂。
- 审查指出本次改动的可读性问题。

### 不必套用的情形

- 不理解原代码为何存在时。
- 仅为统一个人风格而整理无关代码。

### 输入

- 代码及调用关系。
- 现有测试、异常行为和项目约定。
- 解释历史原因的变更记录。

### 执行步骤

1. 先理解职责、边界和历史原因，确认哪些行为必须保留。
2. 识别具体障碍，如嵌套深、命名含糊或重复校验。
3. 按项目风格一次整理一小处。
4. 每次修改后验证，不靠改掉原测试来通过。
5. 比较前后是否更易读，检查没有夹带新功能。

### 产出

- 范围清楚的重构代码。
- 行为未变的检查证据。
- 整理理由与保留约束的说明。

### 原理

先用“为什么原来这样做”约束助手，再用行为不变和逐步验证限制修改范围，把重构从个人偏好转为可检查的维护工作。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：整理虚构资料检索小工具的结果函数。

**起点：** 读取、筛选、排序和格式化出处混在一起，空结果路径难辨认。

1. 确认匹配、排序、错误及数量规则。
2. 提取有明确名称的出处格式化函数。
3. 用相同虚构资料比较前后结果和错误。

**预期产物：** 目标是职责清楚但行为相同的代码，不增加新算法。

**验证方法：** 已有用例不变且通过，并人工检查副作用和可读性；尚未执行。

### 边界与配合

- 不能自动发现需求错误，也不是性能优化。
- 有限测试不能证明所有行为等价。
- 上游行数建议须结合项目判断。
- 配合 [代码审查与质量判断](#code-review-and-quality)：审查指出哪里难懂，简化实施整理。
- 配合 [测试驱动开发](#test-driven-development)：行为测试保护重构。
- 配合 [Git 工作流与版本](#git-workflow-and-versioning)：分开重构和功能修改，便于审查和回退。

## 18 · 安全检查与加固

**阶段：** 审查 · **原名：** `security-and-hardening`

先识别信任边界和待保护资产，再针对输入、授权、敏感信息、依赖和外部服务设计检查与防护。

### 适用情形

- 接收输入、上传文件、处理登录权限或调用外部服务。
- 加入依赖、处理敏感资料，或把模型输出用于界面与工具。

### 不必套用的情形

- 把检查清单当成全面安全认证或法律结论。
- 没梳理数据流就机械添加配置。

### 输入

- 数据流、入口、权限和待保护资产。
- 实际代码、锁文件和部署配置。
- 数据保护要求与已授权范围。

### 执行步骤

1. 标出不可信数据入口，明确需要保护的资料和权限。
2. 从冒充、篡改、泄漏、拒绝服务、越权等角度构造滥用场景。
3. 在边界校验输入，限制权限，并正确编码输出。
4. 检查密钥、日志、上传、URL 请求、依赖脚本和模型输出。
5. 用针对性测试及实际响应验证，记录风险和未覆盖部分。

### 产出

- 威胁与信任边界说明。
- 对应风险的代码或配置改动。
- 异常输入测试及未解决风险记录。

### 原理

把“注意安全”转成“谁写入这个值、它会被拿去做什么、如何限制”的问题链。真正的边界要落实到代码和平台权限，提示词本身不是防护。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：给虚构资料检索小工具增加导入。

**起点：** 标题直接插入页面，文件大小和字段类型没有限制。

1. 定义允许的字段、数量和大小。
2. 以文本显示标题，拒绝非法字段和重复标识。
3. 避免在日志记录完整正文，模型输出同样只当数据。

**预期产物：** 目标是输入范围明确、失败时不覆盖原资料的导入设计。

**验证方法：** 用虚构非法字段、脚本样式文本和超限文件验证拒绝或安全显示；未执行。

### 边界与配合

- 一次审查不能保证无漏洞；依赖扫描主要发现已知风险。
- 法律与配置示例须结合实际环境核实。
- 上游删除、迁移和审批建议不覆盖用户授权及 ReflectFlow 保护。
- 配合 [接口与契约设计](#api-and-interface-design)：接口契约确定边界，安全检查能否绕过。
- 配合 [运行观测与诊断信息](#observability-and-instrumentation)：日志既要能诊断，也要避免泄漏。
- 配合 [持续集成与自动化](#ci-cd-and-automation)：可机械验证的规则可以自动执行。

## 19 · 性能测量与优化

**阶段：** 审查 · **原名：** `performance-optimization`

建立可比较基线，定位瓶颈，修改后重新测量，并区分随机波动与真实改善。

### 适用情形

- 用户反馈慢、指标退步或项目有明确性能目标。
- 资料量与请求量增加后需要定位瓶颈。

### 不必套用的情形

- 没有证据就添加缓存、索引或复杂优化。
- 用单次跑分快了证明真实用户体验提升。

### 输入

- 代表性数据、设备和网络条件。
- 加载、交互、查询或资源占用的测量方法。
- 正确性检查和项目性能目标。

### 执行步骤

1. 固定条件记录基线，区分实验室和真实用户数据。
2. 检查网络、主线程、查询计划或资源等待，定位瓶颈。
3. 一次修改一个有证据支持的环节，考虑维护成本。
4. 在相同条件下重复测量，比较差异是否超过波动。
5. 保留有效且正确的改动，记录无效尝试，设置回归检查。

### 产出

- 可重现条件和前后数据。
- 与瓶颈对应的改动。
- 失败尝试记录及性能回归监测。

### 原理

把优化当作实验假设，要求同条件、单项变化和重复测量，避免把热缓存、随机波动或少做必要工作误认为进步。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：虚构资料检索小工具在大量结果时卡顿。

**起点：** 每次输入都重建全部结果卡片，但不清楚慢在检索还是渲染。

1. 固定虚构资料，分别测检索和渲染。
2. 若瓶颈在 DOM 更新，再尝试分页或分批渲染。
3. 重复同样测量，检查结果及来源仍正确。

**预期产物：** 目标是有测量依据的改动；收益不足则保留简单方案。

**验证方法：** 记录原始数据、波动、前后差异及正确性，不编造提升数字。

### 边界与配合

- 不自带分析器，依赖工具和代表性环境。
- 实验室分数不能代替用户数据。
- 上游预算数字是示例，非所有项目标准。
- 配合 [浏览器运行验证](#browser-testing-with-devtools)：提供运行轨迹、网络和交互证据。
- 配合 [运行观测与诊断信息](#observability-and-instrumentation)：观察真实使用及性能回退。
- 配合 [质量约束与检查门槛](#constraint-driven-development)：确定项目真正关心的性能目标。

## 20 · Git 工作流与版本

**阶段：** 维护 · **原名：** `git-workflow-and-versioning`

把变更组织成有单一目的的提交和工作分支，用标签、版本号及面向使用者的更新说明表达发布内容。

### 适用情形

- 提交、分支、冲突处理、整理混杂修改或并行开发。
- 发布被其他人依赖的软件，需要说明升级影响。

### 不必套用的情形

- 因技能建议频繁提交就擅自提交、推送或重置用户工作。
- 把 Git 当作未跟踪文件和运行数据的完整备份。

### 输入

- 分支、差异和各项修改归属。
- 仓库提交及分支约定。
- 验证结果、兼容性和发布范围。

### 执行步骤

1. 查看工作区和约定，分清本任务与其他修改。
2. 按逻辑目的组织变更，需要时用分支或工作树隔离。
3. 检查待提交内容、敏感信息与验证结果，再按授权保存。
4. 用消息解释原因，分开格式、重构和功能变化。
5. 发布时按兼容性选择版本，用标签锁定产物并记录用户影响。

### 产出

- 可审查的提交序列。
- 锁定变化的版本标签。
- 更新日志和必要的迁移说明。

### 原理

将快速产生的修改切为可理解的保存点，用分支隔离、历史追溯。区分开发者看的提交记录与使用者关心的版本契约。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：虚构资料检索小工具增加分页并修复出处显示。

**起点：** 两项行为变化和整页格式化混在一起。

1. 先分清哪些差异属于本任务。
2. 将出处修复与分页分别组织，附各自验证。
3. 按约定记录使用者可感知的版本变化。

**预期产物：** 目标是能单独理解和追踪的变更；尚未提交或发布。

**验证方法：** 核对每项差异与目的，确认未包含他人工作且有相应验证。

### 边界与配合

- 分支时长、行数和提交频率是建议，须服从项目约定。
- 代码回退不恢复数据库和未保存内容，不应照抄破坏性重置示例。
- Git 不能代替数据备份和完整性核查。
- 配合 [增量实现](#incremental-implementation)：功能切片提供可保存的小步成果。
- 配合 [代码审查与质量判断](#code-review-and-quality)：清楚边界让审查更容易。
- 配合 [发布与上线验证](#shipping-and-launch)：版本定义发布哪个产物，上线技能负责交付。

## 21 · 持续集成与自动化

**阶段：** 维护 · **原名：** `ci-cd-and-automation`

把认可的质量检查及构建发布步骤写进流水线，尽早反馈问题；正确配置平台后，可阻止失败变更进入后续流程。

### 适用情形

- 建立或修改构建、测试和发布流程。
- 需要自动验证，或流水线缓慢、脆弱、失败难处理。

### 不必套用的情形

- 只有配置文件，没有真实运行和阻断证据。
- 为了变绿而降低标准或跳过失败测试。

### 输入

- 项目真实安装、检查、测试和构建命令。
- 环境、锁文件与测试服务。
- 平台权限、凭据隔离和阻断规则。

### 执行步骤

1. 确认本地可运行检查及依赖，按成本安排顺序。
2. 设置触发条件，在可复现环境执行。
3. 配置必需状态检查，验证失败真的能阻止目标操作。
4. 保存失败输出，修复后重新验证。
5. 按需接入预览和发布环境，分离测试与生产凭据。
6. 用缓存和并行缩短等待，不能隐藏错误。

### 产出

- 流水线配置与运行记录。
- 成功和失败的反馈。
- 实际生效的检查及交付规则。

### 原理

将其他技能中可执行的文字要求转成重复运行的程序。只有检查确实运行、平台规则确实生效，才形成约束。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：每次修改虚构资料检索小工具都检查匹配和出处。

**起点：** 开发时测过一次，之后容易忘记复查。

1. 把关键词、空结果和出处检查整理成命令。
2. 让合并请求运行并保存结果。
3. 在隔离分支用已知错误验证失败，修复后确认通过。

**预期产物：** 目标是重复验证和阻断证据，不只是绿色图标。

**验证方法：** 正确版本通过、错误版本失败，并核实阻断规则；尚未执行。

### 边界与配合

- 只覆盖写进检查的行为，不能替代需求判断。
- 配置文件不等于分支保护已启用。
- 平台与命令示例须按实际栈、版本和授权调整。
- 配合 [质量约束与检查门槛](#constraint-driven-development)：先确定底线，再选择自动阻断项。
- 配合 [测试驱动开发](#test-driven-development)：提供可执行行为检查。
- 配合 [发布与上线验证](#shipping-and-launch)：流水线执行步骤，上线技能确定完整发布条件。

## 22 · 弃用与迁移

**阶段：** 维护 · **原名：** `deprecation-and-migration`

先确认替换必要性和依赖者，准备可用替代方案，再分阶段迁移与核验，最后处理旧实现。

### 适用情形

- 更换系统、接口、数据结构或依赖。
- 准备停用功能或减少重复实现的维护成本。

### 不必套用的情形

- 仅因被忽略、久未修改或像缓存就删除。
- 替代方案尚未覆盖关键用途就强制切换。

### 输入

- 旧方案用途、实际消费者和兼容行为。
- 替代方案与迁移成本。
- 保护要求、恢复条件和明确授权。

### 执行步骤

1. 确认旧方案价值，盘点依赖者并比较迁移与维护成本。
2. 先验证替代方案，准备具体说明或工具。
3. 按调用方或数据批次迁移，必要时保留适配层和开关。
4. 结构变更先新增兼容字段，再补数据、切换读写，最后单独收缩。
5. 每阶段核对数据、行为和恢复路径，并观察旧方案使用情况。
6. 证据充分且操作获授权后，才处理旧实现。

### 产出

- 依赖清单及分阶段计划。
- 兼容适配、迁移工具和核验记录。
- 经过验证的恢复路径及退役依据。

### 原理

把一次破坏性替换拆成可观察阶段，确保转换期新旧方案兼容。新代码部署成功并不等于迁移完成。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：把虚构资料检索工具的出处字符串改为结构化字段。

**起点：** 旧记录只有 source，新页面需要文档名和段落号。

1. 增加新结构并继续识别旧格式。
2. 在虚构副本转换，无法推断的字段保留未知。
3. 比较前后资料、出处和结果，确认旧调用方情况再规划停用。

**预期产物：** 目标是兼容过渡和核对记录，不是覆盖原文件。

**验证方法：** 检查字段保留、未知值、重复执行及旧版读取；未实施迁移。

### 边界与配合

- 数据删除可能不可逆，不能用代码回滚代替恢复。
- 通用建议不授权清理本机数据，ReflectFlow 保护继续有效。
- 无引用或低调用量不证明没有离线或外部消费者。
- 配合 [接口与契约设计](#api-and-interface-design)：契约帮助判断消费者受何影响。
- 配合 [增量实现](#incremental-implementation)：按兼容阶段逐步实施。
- 配合 [运行观测与诊断信息](#observability-and-instrumentation)：使用信号帮助确认旧路径是否还有消费者。

## 23 · 文档与决策记录

**阶段：** 维护 · **原名：** `documentation-and-adrs`

记录运行方法、接口行为和重要选择的理由，用架构决策记录保存背景、替代方案、取舍和后果。

### 适用情形

- 选择重要依赖、数据结构和架构。
- 修改接口、发布功能，或反复解释同一问题。

### 不必套用的情形

- 逐句解释显然的代码，或为一次性试验制造大量文档。
- 为让文字好看而删掉限制、把未验证内容写成保证。

### 输入

- 代码、真实命令和已有文档格式。
- 背景、要求、备选方案和取舍。
- 需保留的约定、限制及未决事项。

### 执行步骤

1. 检查已有位置、编号和模板，沿用仓库约定。
2. 记录重要选择的状态、背景、决定、替代方案和后果。
3. 补齐运行方法、接口参数、返回值和错误。
4. 在合适位置解释难从代码看出的原因和陷阱。
5. 核对命令与事实，保留条件和不确定性。
6. 决定改变时新建关联记录，保留旧决定的历史理由。

### 产出

- 可执行的使用说明和接口文档。
- 有状态的架构决策记录。
- 有依据的约定、限制和更新说明。

### 原理

将代码里缺少的设计背景外置保存，尤其解释原因并保留历史，让未来助手不必凭当前代码猜测过去约束。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：解释虚构资料检索小工具为何先用关键词搜索。

**起点：** 后续读者可能以为遗漏向量检索，直接增加模型依赖。

1. 写明当前目标是少量虚构资料的可解释基线。
2. 比较关键词与语义检索取舍，写明什么证据会促使重评。
3. 补充输入、命令和出处规则。

**预期产物：** 目标是让后续实施者理解选择和重评条件的记录。

**验证方法：** 按说明重跑样例，逐项核对事实；本教学文档方案未执行。

### 边界与配合

- 文档须随行为和决定更新，不会自动保持准确。
- 记录选择不代表选择普遍最优。
- 模板日期、数字和示例不能当成项目事实。
- 配合 [规格驱动开发](#spec-driven-development)：规格定义要做什么，决策记录解释为何这样实现。
- 配合 [上下文组织与交接](#context-engineering)：可靠文档成为按需读取的上下文。
- 配合 [Git 工作流与版本](#git-workflow-and-versioning)：版本帮助文档对应具体产物。

## 24 · 运行观测与诊断信息

**阶段：** 维护 · **原名：** `observability-and-instrumentation`

从具体问题出发设计日志、指标、调用追踪和告警，并验证这些信号能帮助定位问题。

### 适用情形

- 新增服务、后台任务、外部调用或重试。
- 缺少事故记录，或需要调整告警。

### 不必套用的情形

- 把加监控等同于已找到当前故障原因。
- 把日志量或漂亮仪表盘当作健康证明。

### 输入

- 运行架构、入口与异步路径。
- 需要回答的少量运维问题。
- 敏感字段边界、运行目标和监测平台。

### 执行步骤

1. 先写清两到四个问题，如失败比例和慢在哪里。
2. 选择日志记录个例、指标观察整体、追踪拆分跨环节耗时。
3. 用事件名与关联标识串起请求，多入口共用日志时标明入口。
4. 限制指标标签和日志字段，不记录敏感正文。
5. 按用户感知异常设计告警，并附第一步处理方法。
6. 触发测试故障，确认信号和通知实际可用。

### 产出

- 结构化日志、聚合指标与必要追踪。
- 有阈值和处理说明的告警。
- 靠运行信号定位测试故障的证据。

### 原理

把“记录更多”变成“每条信号回答一个问题”。日志解释个例，指标显示趋势，追踪拆分耗时；监测代码本身同样要验证。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：让虚构资料检索小工具解释搜索失败。

**起点：** 只显示失败，无法区分载入、检索或渲染环节。

1. 为查询生成关联标识，分别记录阶段完成与失败。
2. 只记耗时和错误类别，不记录查询与资料正文。
3. 模拟格式错误，尝试仅靠信号定位阶段。

**预期产物：** 目标是能说明故障环节和影响范围的记录。

**验证方法：** 确认信号产生、字段可查且无敏感内容；尚未执行。

### 边界与配合

- 无法恢复从未记录的事件，也不单独证明数据完整。
- 监测有存储和运行成本，须控制信息量。
- 小型离线工具无需照搬复杂服务监控。
- 配合 [系统调试与恢复](#debugging-and-error-recovery)：为调试提供可核对的证据。
- 配合 [性能测量与优化](#performance-optimization)：提供瓶颈线索，优化负责实验。
- 配合 [发布与上线验证](#shipping-and-launch)：提供上线与回退判断所需信号。

## 25 · 发布与上线验证

**阶段：** 维护 · **原名：** `shipping-and-launch`

连接发布前检查、逐步开放、运行观察和回退准备。上传成功之外，还需确认目标环境的关键流程正常。

### 适用情形

- 首次发布、重要更新、测试版开放或风险部署。
- 需要明确上线条件、观察项和回退规则。

### 不必套用的情形

- 用本机测试或部署命令成功代替完整验收。
- 未经授权发布、通知他人或回退数据。

### 输入

- 确定版本及验证结果。
- 目标环境、使用范围和关键流程。
- 观测信号、恢复准备及发布授权。

### 执行步骤

1. 核对代码、安全、性能、可访问性、环境和文档准备。
2. 明确成功、暂停和回退条件，验证恢复机制。
3. 先验证测试环境，再按实际需要逐步开放。
4. 每次扩大范围后观察错误、响应和使用情况。
5. 上线后再走关键流程、检查日志，处理阶段性开关。

### 产出

- 有证据的发布检查。
- 分阶段计划与观察结果。
- 可执行回退说明及实际版本状态。

### 原理

分开部署动作和开放决定：代码可以先部署而不启用，再按观测结果决定继续、暂停或回退。以此控制影响范围。

### 教学示例（未执行）

**任务：** 教学示例（未执行）：公开虚构资料检索小工具的新版结果页。

**起点：** 本地正常，正式路径、资料加载和出处链接尚未确认。

1. 在预览环境检查查询、空结果、错误输入及出处跳转。
2. 准备旧版本，约定暂停条件。
3. 若实施发布，再检查正式地址和错误记录。

**预期产物：** 目标是可追溯上线证据和恢复准备；未实际部署。

**验证方法：** 必须看到目标环境运行结果，不能仅看构建成功或本地截图。

### 边界与配合

- 开关不能撤销已有数据变化，代码回退不等于恢复数据。
- 比例、观察时长和阈值示例须按风险调整。
- 依赖部署工具和权限，不自动提供托管能力。
- 配合 [持续集成与自动化](#ci-cd-and-automation)：执行重复检查和部署，上线技能完成整体验收。
- 配合 [Git 工作流与版本](#git-workflow-and-versioning)：锁定发布版本和更新说明。
- 配合 [运行观测与诊断信息](#observability-and-instrumentation)：支持继续、暂停或回退判断。
- 配合 [弃用与迁移](#deprecation-and-migration)：涉及格式替换时处理兼容与数据过渡。
